## 已确认的展示规则

一次初始请求、共同起始状态与公开历史进入 E/A/N/S 四个独立分支。后台可并行处理，但**首次结果必须统一展示**。即使 E 已完成，也不能在 A/N/S 的澄清得到处理前，提前显示修改结果、回答、外观或声音。

澄清阶段可以查看和回答各分支的待确认问题。只显示共同基线、问题与选项及中性处理状态；不显示完成分支的新属性值、回答、修改历史或音频资源。回答后若仍有澄清或生成工作，继续等待。所有分支结果准备完毕才一次性开放比较。

失败不自动算完成；提供重试或明确结束该分支。明确结束记为 incomplete，取消或无法执行也分别记录，不能假装成功。退出整个任务随时可用，不会强制公开未完成结果。

首次开放后，用户可自由切换和修复。首次结果固定保存，后续结果单独更新；已经看到的信息无法通过再次隐藏消除，因此本次约束明确针对首次展示。

### 状态与开放条件

任务阶段由分支状态推导，避免任意直接赋值绕过限制：

`awaiting_input → preparing / clarifying / needs_attention → ready_to_reveal → revealed`

任何阶段可终止为 `closed`。当前 close 是终止，不能冒充可恢复的暂停；暂停在第 5 步实现。

分支状态：idle、processing、awaiting_clarification、ready、failed、stopped。

- `ready`：控制器确认当前澄清及生成均已处理，结果为 completed / cancelled / unresolved。
- `failed`：尚待重试或显式结束，**不满足开放条件**。
- `stopped`：用户/研究者明确结束分支，结果为 incomplete；不能因超时自动设置。
- 全部分支为 ready/stopped 时只进入 ready_to_reveal，结果仍隐藏。后续调度器调用 `reveal`，在同一锁内固定四份快照并一次性开放。

`completed` 只表示工程处理完成，不表示参与者目标达标；任务达标仍由问卷判断。

### 视图分离

`participant_view()` 是后续 UI API 唯一允许公开的投影。首次开放之前：

- 保留共同 baseline，前端须将 avatar、属性和历史固定在此基线上。
- 显示待回答问题及选项、通用错误类别；不输出 provider 原始错误或隐藏回答。
- 四分支 `result` 均为 null，`first_reveal` 为 null；ready/stopped 对外统一标记 waiting。
- 切换分支只改变选中标识，不改变结果可见性，不重置该分支。

开放后，同一份视图返回四分支结果及固定 first_reveal。发生后续修复时，当前结果可继续变化，但首次快照保持不变。当前分支版本可供后续绑定评价、提醒重新评价；本步骤没有实现问卷或正式提交。

`worker_input(ticket)` 是**服务端内部数据**，包含独立 TutorState 副本和所属分支已回答的澄清；不可作为 UI 响应或直接传给模型。共同解释输入用 `initial_model_context()`，复用公开上下文白名单，排除任务标识、情境、策略标签和私有目标。

### 控制器调用契约

| 方法 | 职责 |
| --- | --- |
| start | 固定共同请求，为四个分支发放处理凭据。 |
| ask | 保存经过校验的公开澄清；旧处理凭据随状态变更失效。 |
| answer | 校验分支、问题和版本，保存选项或转写文本，发放新处理凭据；不会自行解释或提交修改。 |
| finish | 接收独立 TutorState 及明确结果状态，保存隐藏结果。仅供控制器在确认澄清/生成完成后调用。 |
| fail / retry | 保留失败状态，显式重试发放新凭据。模型重试/HTTP 幂等仍在第 3 步实现。 |
| stop_branch | 明确结束未完成分支，并使在途结果失效；后续 API 须确保对应用户/研究者操作。 |
| reveal | 检查所有分支准备状态，原子固定首次快照并开放。 |
| begin_repair | 首次开放后，用新的分支请求启动修复；保留其他分支与初始上下文。 |
| select / close | 只切换选中分支，或终止本次比较；关闭后的结果更新被拒绝。 |

## 第 2 步：共同初始解释与只读策略决策

实现：`Backend/tutor_shared_request.py`、`Backend/tutor_policy.py`；测试：`Backend/tests/test_tutor_shared_request.py`。现有 `TutorSessions` 也使用抽取后的同一策略判断，保留原有行为和日志，不维护第二套 S 规则或 N 提示。

### 处理顺序

1. `comparison.start(...)` 固定共同请求和起点；`comparison.shared_initial(model)` 获取本题唯一的准备对象，获取对象本身不调用模型。
2. 第一次 `prepare()` 通过已有 TutorInterpreter 解释共同请求，完成候选校验、相同效果去重和默认 ID 映射，并生成一份共同问题/选项。后续调用返回副本，不再次解释。
3. `input_for(ticket)` 将同一 `shared_id`、解释、候选、默认值及问题交给对应分支。各输入只有策略/分支路由标识不同；这些路由标识不进入解释模型或 N 的模型上下文。
4. `decision_for(ticket)` 给出只读决策：E 执行共同默认候选，A 询问，S 使用现有规则，N 单独调用决策模型。此时不修改分支设置、不生成回答、不向参与者公开结果。
5. 第 3 步的调度器再根据计划调用比较状态模块；提交时继续核对 WorkTicket，ASK 才发布本分支的问题，生成完成才调用 finish，满足统一条件才 reveal。

普通知识请求只有一次共同解释，各策略均走 CHAT_QUEUED，不额外调用 N 决策。不支持的请求统一 UNRESOLVED，不给 E/N 额外修改能力。混合请求的学习问题、持续/单次作用范围原样保留。

### 共享范围与隔离

- 共同基线包含公开设置、公开历史和公开偏好；不包含 task_code、task_id、情境、评分或研究者私有目标。
- N 使用相同公开上下文、同一解释和共同问题，不接收 S 的判断规则或其他分支决策。只能返回 ASK/ACT/UNRESOLVED 及原因，不能附加新 patch 或改候选。
- 准备结果带 `shared_id`、`context_sha256`、解释版本和基线状态版本。返回值全部脱离内部缓存，调用者和模型不能通过修改返回对象污染其他分支。
- 共同问题在此不带 question_id。第 3 步为实际 ASK 的分支分别建立独立问题 ID，问题文字、选项和顺序仍来自同一份共同内容。
- 只有未处理的初始 WorkTicket 能走共享入口。回答已有澄清以及展示后的修复必须使用所属分支上下文，即使修复措辞与初始请求完全相同也不能复用初始路径。
- 不同任务尝试各有独立解释；不能因为文字相同就跨任务复用。当前成功结果也不能通过更换模型对象在同一任务内重生成。

### 并发、缓存与失败

- 多个分支同时请求初始解释时，只有一个调用执行解释，其余复用完成结果。每个策略的决策缓存独立，N 的慢调用不占用比较状态锁或 E/A/S 的决策锁。
- 失败也缓存：解释失败不会因四分支分别请求而连续再调用四次。`retry_preparation(expected_attempt=...)` 只允许明确重试当前失败的尝试；成功解释不可重生成。
- N 决策失败只影响 N。`retry_decision(...)` 只重试该决策，保留原共同解释，E/A/S 仍可获取自己的计划。重复或过期的重试编号被拒绝。
- “一次共同解释”指共享层只发起一个解释操作；模型适配器内部的 provider 重试仍由该适配器配置控制，实际尝试应按 model_calls 统计，不能简单把解释操作数当作计费调用数。
- 解释期间关闭任务后，不发布迟到结果；分支已停止或凭据失效后，不返回可提交的初始计划。调用计划之后的真正状态提交仍需由状态层再次校验凭据。

### 记录与展示边界

`prepare()` 保留共同解释的 model_calls；`input_for()` 不向四份分支输入复制这条调用记录。每个决策只携带自己的调用记录（E/A/S 通常为空，N 有单独记录）。`status()` 可读取各操作尝试与成功/失败记录，但目前这些记录只在内存中；第 3 步接入持久日志时，应将共同解释记录一次并由四分支引用 shared_id。

prepare、input_for、decision_for 和 status 都是服务端内部接口，**不能接到参与者可见的调试响应**。`participant_view()` 未增加候选或决策字段，首次展示约束不变。生成计划并不等于已展示问题或结果。

## 第 3 步：异步执行、HTTP、恢复与自动统一展示

实现：`Backend/tutor_comparison_service.py`，接入 `Backend/server.py`。接口详见 [四策略比较 HTTP 契约](COMPARISON_BACKEND_API.md)。保留原 `/sessions` 和 `/tutor/sessions` 行为。

### 执行与展示

1. 创建 debug 比较任务，共同公开设置、偏好与历史复制到四个私有会话；这些会话不注册到旧单会话 API，不能从旧接口提前读取结果。
2. start 接收一次共同请求并立即返回 202；共同解释完成后，由工作线程分别执行 E/A/N/S。慢 N 或某分支失败不占用其他策略的执行锁，GET 可继续轮询。
3. 初始策略复用第 2 步计划，通过原会话引擎提交修改、建立澄清或生成回答。澄清回答按分支和 question_id 路由，接受选项或转写后的文本；尚未接入麦克风/STT。
4. 所有分支的澄清和生成处理完毕（或明确停止为 incomplete），先写入 first_reveal 日志，再原子开放四份结果。结果隐藏期间禁止直接控件/新请求绕过澄清流程；普通响应、错误响应和重复请求响应均使用同一参与者视图。
5. 开放后，各分支可继续对话、调整 Reply length 或撤销。首次结果快照固定，后续修复只更新所属分支。

同题内实际生成上下文完全相同时，复用一次有效生成结果，分别写入各分支历史，避免等效策略因随机措辞产生差异。上下文含学习问题、回答结构及已完成的公开对话；任一不同则独立生成。未来接入 Tone 等生成属性时，必须同步扩展生成上下文。不同任务不共用缓存。

### 恢复与记录

- 所有 POST 使用 request_id 去重；任务操作校验 expected_revision，分支操作只校验 expected_branch_revision。重复请求不会重复提交或增加模型调用。
- 共同解释失败用 retry_shared；分支执行/生成失败用对应 retry。已提交的修改通过检查点保留，生成重试不重复修改。所有分支明确停止后不能再次启动共同解释。
- 日志写入失败不提交未记录的检查点；首次展示日志失败则继续隐藏，使用 retry_reveal 重试。缓存仍有效时复用已有模型结果；若失败发生在结果进入缓存前，明确重试可能重新调用模型。
- stop/close 使在途处理凭据失效；迟到结果不能覆盖状态。已经发出的 provider 请求未必能中断，仍记录其实际返回。
- JSONL 保存共同解释、策略计划、引擎尝试、分支提交检查点、生成复用引用及首次展示快照。provider_started/provider_finished 是规范的调用记录；其他事件引用的 model_calls 不应重复计数。

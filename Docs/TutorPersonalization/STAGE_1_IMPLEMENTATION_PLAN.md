## 目标与范围

先让一个属性真正贯穿“自然语言请求 → 策略处理 → 设置提交 → 实际回答 → 后续对话 → 面板与历史”。首个属性为 Reply length。它不依赖 TTS，适合先验证公共链路；语音输入、实际声音及四策略并行比较随后接入。

阶段一完成后，应能从 Balanced 开始，提出 “Give me only the key points from now on.”，按当前策略执行或确认后进入 Brief；接着问学习问题，实际回答只保留关键点；追问保持 Brief；面板和修改历史与后端一致；撤销回答长度不会恢复其他已修改的属性。

实现依据为 [最终四策略研究设计](Study/FINAL_USER_STUDY_DESIGN_4_STRATEGIES.md) 和 [三视图面板设计](PANEL_DESIGN_V2.md)。工程测试可直接提供文本/API 请求；最终参与者使用英文语音，不把开发测试入口变成正式实验中的文本输入要求。

## 当前代码核对

- `Backend/core.py`、`model.py`、`server.py` 已有外观解释、E/A/N/S、澄清、撤销及 HTTP 接口；模型接口目前主要生成外观修改候选和 Native-gate 决策，不是完整 tutor 问答链路。
- `study-v1` 与 `avatar-demo-v1` 不包含四项对话属性。旧研究的轮次、修复预算和仅首次请求过策略等规则不能直接当作新研究规则。
- `SettingsPanelDemo.cs` 中四项属性只改变演示值，不影响模型输出或音频。
- 已接受的 HTML 面板是交互设计预览，尚未成为已连接后端的 Unity 面板。

新增 tutor 模块分步接入；现有外观接口和旧研究配置保留。当前不注册新正式研究配置，也不把工程测试结果写作参与者数据。

### 第 1 步：已落地的状态契约

实现：`Backend/tutor_state.py`；测试：`Backend/tests/test_tutor_state.py`。

| 字段 | 后端值与默认值 | 说明 |
| --- | --- | --- |
| `speech_rate` | 默认 `1.0`；当前应用范围 `0.70–1.30`、精度 `0.01` | 延续本地面板；1.0 指模型/当前声线默认语速。不是已验证的 TTS 能力范围。 |
| `reply_length` | `brief / balanced / detailed`；默认 `balanced` | 关键点 / 关键点＋简短理由 / 关键点＋解释及适用的例子或步骤；不以句数或字数定义。 |
| `tone` | `professional / friendly / encouraging`；默认 `professional` | 语气风格，当前建立状态，尚未接实际生成。研究默认值采用设计文档，而非演示面板当前选项。 |
| `voice` | `voice_a / voice_b / voice_c`；默认 `voice_a` | 应用内稳定标识；真实声音和供应商 ID 待语音阶段映射，尚不能播放。 |
| 外观字段 | `avatar_id / outfit / jacket_color / accessory / scale` | 复用现有外观验证；默认 Liang、蓝色西装、眼镜、1.0。 |

当前 `TutorState` 提供：

- `snapshot()`：脱离内部对象的状态副本，包括版本、设置、修改历史和对话历史。
- `commit(...)`：只供明确控件操作或已完成策略决策的控制层调用。包含来源、请求文本、前后值和实际变更字段；非法组合整体拒绝，不做部分提交。不变的设置不会制造虚假变更记录。
- `undo(field, ...)`：撤销该字段最近一次仍可撤销的修改，保留其他字段；`all` 撤销最近一次仍可撤销的整项修改。无法成立的外观组合拒绝执行，不自动替用户改其他字段。
- `record_exchange(...)`：成对记录成功的用户问题和 tutor 回答，并保存生成时设置。设置/对话版本改变后的旧结果拒绝写入。

所有写入必须匹配当前 `expected_revision`，成功操作增加版本号；并发写入使用锁。不同实例不共享设置和历史。对话历史与属性修改历史分开存储，后续分别映射 Conversation 与 History。

该状态模块仅使用内存，不自行调用模型；第 2 步的解释器接入模型，第 3 步的会话控制器已接入 HTTP 路由、策略决策及待确认生命周期。`commit` 不自行决定 ASK/ACT，控制层保证调用条件。目前没有磁盘恢复；第 5 步通过 HTTP 绑定 Unity。创建四个独立实例不等于已实现四策略并行实验。问卷、私有目标和参与者标识不进入设置结构。

语速 `1.2 × 0.9 = 1.08` 已可存储，但**尚未实现自然语言中“正常语速的 0.9 倍”与“当前的 0.9 倍”的判别**。后续解释器必须明确基准，真正含糊时提供不同候选；不能把所有倍率默认乘当前值，也不能静默截断到范围边界。

### 第 2 步：已落地的请求解释

1. 定义解释结果，区分普通问答与定制；混合请求要同时保留问题和修改意图，不能丢失任一部分。
2. 复用已有模型适配器和环境中的模型配置，不把模型名称写死在新业务模块中。
3. 首先支持 Reply length 的明确结构要求、小幅结构调整、跨属性竞争解释及公开历史恢复。尚未实现的其他属性定制应明确返回未支持，不偷偷转换成长度修改。
4. 候选生成读取当前公开设置、必要的对话/修改历史及公开软偏好；不读取研究者私有目标、评分或策略标签。
5. 用固定模型返回值测试分类、候选校验和无副作用，再检查实际模型解释。测试样例不是要求参与者照读的句子。

实现：`Backend/tutor_interpretation.py`；`Backend/model.py` 新增 `interpret_tutor`，复用既有模型配置、传输和调用记录；测试：`Backend/tests/test_tutor_interpretation.py`。

入口为 `TutorInterpreter(model).interpret(query, snapshot, preferences=..., pending=...)`。结果包括原始请求、所依据的状态版本、解释结果和模型调用记录，不包含执行决定，也不会调用 `commit`。

| 解释类型 | 含义 | 主要输出 |
| --- | --- | --- |
| `chat` | 普通知识问题或讨论 | 保留原始问题；无修改候选 |
| `tailoring` | 单纯修改要求 | 字段、作用范围、共同候选及解释依据 |
| `mixed` | 修改要求＋学习问题 | 同时保留候选和学习问题；不直接生成答案 |
| `clarification` | 回答已有待确认问题 | 已提供的选项 ID、取消，或保留原话供重新解释 |

作用范围分为 `session`（持续设置）、`turn`（明确只针对本次回答）、`unspecified`（无法判断）。普通设置请求默认持续，明确单次要求不转换成长期偏好；范围不明时不生成可执行候选。解释层识别范围，第 3 步将单次覆盖绑定到问题而不修改持久设置，第 4 步按该绑定生成并记录实际回答。

公共上下文仅提取当前设置、最近 20 项修改、最近 6 次问答及至多 10 项公开偏好；修改和问答带公开序号便于恢复先后关系。策略标签、参与者标识、任务目标及问卷评分不进入上下文。超出历史窗口的信息不可假装仍被记住，历史不足时允许返回未解决。

候选仅允许 `reply_length`，按最终效果去重，默认候选随去重映射。当前值与空修改表示同一结果。跨属性竞争解释或含有未支持字段的组合要求整体保持未解决，不能只取其中可实现部分。返回格式不合法时拒绝使用，并保留调用记录；不会自动换成模拟结果。

澄清解释要求调用方提供公开待确认问题及选项；不存在的问题、未提供的选项 ID 均拒绝。口头重新表述保留原文。第 3 步已实现建立、取消和过期澄清检查。模拟模型不新增基于关键词的“自然语言理解”替代品；单元测试使用明确标记的固定返回值，真实理解另行检验。

### 第 3 步：已落地的策略与会话控制

实现：`Backend/tutor_session.py`；HTTP 接入：`Backend/server.py`；接口与状态规则详见 [Tutor 后端接口](TUTOR_BACKEND_API.md)。

- `/tutor/sessions` 创建独立 debug 会话，固定 E/A/N/S；支持 request、answer、cancel、settings、undo、reset 和 GET 当前视图。旧外观 `/sessions` 保留。
- ASK 保持设置；明确选项或可解析的自由表述完成原请求，不重复运行 gate。每条新的自然语言定制/修复仍经过当前策略。
- S 的长度规则支持历史引用、可能未经授权的软偏好覆盖和离散结构分歧，不套用外观 scale 的小幅调整例外。N 使用独立模型决策调用，只能选 ACT/ASK/UNRESOLVED。
- 单次长度设置不写入持久设置；普通问题和混合请求的学习部分进入 `generation_jobs`，携带对应设置。第 4 步已接入生成：live 适配器返回 `generation_available:true`，问题由 queued 转为 completed。
- 同会话串行处理、校验客户端 revision 和 question_id。相同请求 ID 重试不重复调用模型，返回当前视图；失败也去重。工作副本通过日志提交后才发布，失败不残留半次修改。
- 公开文本偏好经过存储再传回解释器时，允许其规范化的 `{text:...}` 形式；修复了该路径原先再次校验失败的问题。

### 第 4 步：实际回答生成与对话延续

实现：`Backend/tutor_generation.py`；`Backend/model.py` 新增 `generate_tutor`，使用已有本机模型配置；接口为 `/tutor/sessions/{id}/generate`。

- 模型分别生成关键答案 `key_answer`、支持理由 `reasoning`、例子或步骤 `example_or_steps`。程序按 Brief / Balanced / Detailed 选择前一、前二或全部适用部分。不按句数或词数截断。
- 缺少关键答案或结构非法会失败；可选部分省略等同于空字符串，不伪造理由或例子。模型对内容分段仍可能有偏差，不能把格式正确等同于研究任务达标。
- 当前问题读取最近六次成功完成的问答；对话记录只包含用户真正会看到的组合结果，不包含 Brief 未显示的补充部分，也不包含尚未回答的问题。
- 多问题按入队顺序生成。单次覆盖随对应 job 保存，失败重试仍用同样设置；实际问答记录该设置，持久设置不变，后续问题使用持久档位。
- `/request` 或 `/answer` 与 `/generate` 分开提交，生成失败不会回滚已确认的属性修改。新请求 ID 可重试失败 job；同 ID 不重复调用；已完成 job 即使换新请求 ID 也复用原回答，不重复写历史。
- 模型输出经验证，问答与完成状态一起通过工作副本和日志提交。失败不会出现半条用户问答或假 ANSWER。接口仍为 debug；第 5 步已接 Unity，语音尚未接入。

第 5 步现已实现：Unity 自动衔接“请求/确认 → generate → 显示实际回答”，同步 Controls、Conversation、History。前端内部的两次调用不要求参与者再按一次生成按钮。其后的第 6 步继续检查真实场景、交互和错误恢复；不提前将后端测试算作头显验收。

### 第 3–4 步：决策与生成约束

- 普通知识问答不触发修改策略。每条新的自然语言定制或修复请求使用当前策略；回答待确认问题不重新启动一次 Always-ask。
- 明确控件操作直接提交；统一的待确认/忙碌限制必须对四策略一致。
- 所有策略使用相同有效候选和澄清内容；N 仅选择 ASK/ACT/UNRESOLVED，不获得额外工具或私有目标。
- S 的离散长度候选不能机械套用外观 scale 的数值阈值；不同内容结构是真实不同结果。明确单一请求可执行，实质分歧、无法唯一恢复的历史引用和未授权偏好覆盖分别处理。
- 先从共同明确规则与边界用例实现，再记录具体规则版本，不以结果是否支持 S 来修改规则。
- 已实现 `/tutor/sessions` debug 路径、请求编号去重、版本冲突、失败返回、模型调用日志和实际文本生成；Unity 最小接入已完成，头显与真实模型组合验收待第 6 步。
- Brief/Balanced/Detailed 是生成指导，不保证模型每次遵循；工程验收查看真实回答，研究中的结果判断仍由参与者填写问卷。
- 澄清问题和设置确认反馈不冒充知识回答；无权提交的候选不进入已生效设置。
- 真实 API 验证使用现有本机私有配置；密钥不进入 Unity、日志或文档。

### 第 5 步：Unity 的最小接入

以已确认的 Conversation / Controls / History 为目标，沿用原暖色半透明和轻微发光风格，英文界面。首先连接 Reply length：收到后端确认后刷新，失败则保留/恢复后端值。三个长度档位通过稳定字符串映射，避免把 UI 下标当作后端语义。

显示实际对话、待确认问题、设置修改和单项撤销；不继续用硬编码示例冒充真实记录。其余三属性在尚未接生成/声音时说明可用状态，不能暗示已经改变音频。Play sample 的实际音频实现留到语音阶段，维持已确认的紧凑布局。

第 5 步实现与启动方式见 [Unity 接入说明](UNITY_INTEGRATION.md)。已新增独立的 Desktop / VR 场景，保留原始房间与旧外观实验场景。三个页面从同一后端会话读取数据；桌面文本框仅供工程验证，VR 不显示文本框。
